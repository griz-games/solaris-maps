# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A command-line toolkit for building custom galaxy maps for
[Solaris](https://github.com/solaris-games/solaris) and rendering them to SVG. Pure Python, standard library
only, no install step, no package manager, no web app.

It began as a fork of [IHateAttackMaps/solaris-custom-galaxy-editor](https://github.com/IHateAttackMaps/solaris-custom-galaxy-editor)
(Vue + PixiJS). The editor has been removed; what survives is the game's rules, expressed in Python, and the
editor's art, vendored into `solarismap/assets/`. Provenance comments name the upstream function
(`helper.getHyperspaceDistanceByLevel`) rather than a line number, because the file they refer to is no longer
in this repo.

## Primary goal

Produce starting maps for Solaris matches — the flagship is a 36-player one — as JSON the game loads directly,
built by scripts rather than by hand, and checkable without opening a browser.

**There are skills for this.** `.claude/skills/irregular-galaxy/` covers maps that are *grown* -
no symmetry, fairness arranged and measured rather than inherited. `.claude/skills/solaris-map/`
covers maps that are *placed*, and carries the authoring procedure, the
non-negotiable rules, and a troubleshooting table for every validator error. Prefer it over re-deriving any of
that from source.

## Layout

```
solarismap/     the package: rules, geometry, generate, model, validate, inspect, render, specialists
  assets/       vendored game art (~570 KB) + ATTRIBUTION.md
maps/           one script per map: example.py (template), spy_v_spy.py (909 stars, 36 players),
                irregular.py (grown, not placed - the solarismap.generate worked example)
out/            build output. Maps (*.json) are deliverables and tracked; figures (*.svg) are not
docs/           the documentation site, served by GitHub Pages from this folder
  publish.py    the one bridge: copies built figures out of out/ into docs/assets/
figures/        make_figures.py, study.py - the figures in the write-ups; stdlib only
                metric_figures.py, montecarlo.py - draw and sweep solarismap.metrics
tests/          test_solarismap.py
.claude/        skill, /newmap and /checkmap commands, validation hooks, permissions
```

**The builders and the site are separate, and the arrow only points one way.** A map builder
writes into `out/` under the map's own name (`spy_v_spy.svg`) and contains no reference to the
website. The site reads `docs/assets/` under its slug (`spy-v-spy-map.svg`) and contains no
reference to the builders. `docs/publish.py` is the only thing that spans the two, and the
mapping it uses is the `figure` key in `docs/maps.json`. Do not make a builder write into
`docs/`, and do not hand-edit anything in `docs/assets/` — it is generated.

## Commands

```sh
python maps/spy_v_spy.py [--galaxies N] [--render]   # build; validates as it writes
python maps/example.py                               # the template map
python maps/irregular.py [--seed S] [--generator N] [--players N] [--render]   # a grown map
python -m solarismap validate out/<map>.json         # exit 1 if Solaris would reject it
python -m solarismap inspect  out/<map>.json [--json]
python -m solarismap metrics  out/<map>.json [--json]   # fairness, compactness, novelty
python -m solarismap render   out/<map>.json -o out/<map>.svg [--labels] [--scan] [--focus X,Y,R]
python -m solarismap rules [--json]
python tests/test_solarismap.py                      # 110 checks, exits non-zero on failure
                                                     # (three of them need out/spy_v_spy.json built)

python figures/montecarlo.py --generator irregular --draws 100   # a distribution, not a draw
python figures/montecarlo.py --builder maps.irregular:build --draws 100 --figures
python figures/metric_figures.py out/*.json          # draw a set of maps

python docs/publish.py [--check]                     # out/ figures -> docs/assets/; --check exits 1 if stale
python -m http.server -d docs                        # preview the site; fetch() needs HTTP, not file://
```

`python -m solarismap` works from the repo root with no install; the map scripts bootstrap `sys.path`
themselves, so they run from anywhere.

**Determinism is the regression test.** `python maps/spy_v_spy.py` reproduces `out/spy_v_spy.json` byte for
byte — md5 `65bec4a2b2ace345264162effc34902d`. If that changes and you did not change the layout deliberately,
something broke.

## Conventions

- 4-space indent, type hints on public functions, `from __future__ import annotations`.
- Comments explain *why*, and cite the upstream rule when mirroring one.
- Scratch state on a star uses a `_` prefix; `model.galaxy()` strips it on write.
- `solarismap/specialists.json` is generated by `sync-specialists`. Never hand-edit it.
- Never hand-write a star dict — `model.new_star()` emits every field Solaris requires.
- Never patch a map JSON to make validation pass. Fix the builder and rebuild.
- The prose in `docs/content/*.md` is the author's, not yours. Edit it only to correct a factual error —
  a wrong number, a claim the map no longer supports — and change only the words that are wrong. Do not
  add colour, expand a sentence into paragraphs, restructure sections, or volunteer detail the author
  left out; if a map change makes some passage worth rewriting, say so and let them decide.

## Two different questions

`validate` answers *will Solaris load this file*: field types, hard limits, semantic rules. Binary, no
judgement, and a map must always pass. `inspect` plus each builder's own checks answer *is this the map I
meant*: balance, spacing, reachability, whether contested ground is genuinely contested. Map-specific
invariants belong in the builder — see `check()` in `maps/spy_v_spy.py`, which asserts forty-odd properties
and fails the build when one breaks.

`metrics` answers a third, impartial question: *is it fair, compact, interesting* — eleven statistics that
score any map without knowing what it meant to be, and never fail anything. It is the layer the write-ups
compare generators with, and it runs on a map JSON rather than inside a study. Read **METRICS.md** before
interpreting any of its numbers; in particular, a statistic off one map is a draw, not a property of the
generator, and `figures/montecarlo.py` is how you get the distribution.

## Target output: what Solaris actually accepts

Authoritative sources, in the `solaris-games/solaris` repo — **read these, not the public docs**, which are
years stale (they show numeric IDs, omit `infrastructure`, and describe `id` as optional; all three are now
wrong, and `server/config/game/settings/user/customGalaxyExample.json` is stale in the same ways):

- `common/src/types/common/customGalaxy.ts` — the `CustomGalaxy` type.
- `common/src/validation/customGalaxy.ts` — field-level validator with all numeric ranges.
- `server/services/customGalaxy.ts` — semantic validation + conversion into a real game.
- `server/services/gameCreate.ts` — where the above is invoked and settings are derived.

Top level is `{ stars, players?, carriers?, teams? }`, which is what `model.galaxy()` emits. Paste it into
Create Game → Galaxy Type `Custom`; that page's **Validate** button runs the real validator and is the final
word. `solarismap.validate` reimplements it, and `tests/test_solarismap.py` proves it by breaking a valid map
one rule at a time.

### Basic vs advanced mode

A separate **Advanced Custom Galaxy** setting (`advancedCustomGalaxyEnabled`) decides how much of the JSON is honoured:

- **Basic (disabled)** — only `stars` is read. `players`, `carriers`, and `teams` are **ignored entirely**;
  Solaris creates empty players from game settings and auto-spawns home-star carriers. `playerId` on stars acts
  purely as a grouping key: a player's starting stars are all stars sharing their home star's `playerId`.
- **Advanced (enabled)** — `players` becomes **required** (2–64 entries) and supplies credits, tech levels, and
  alias. `carriers` and `teams` are honoured. `teams` is required if the game mode is `teamConquest`.

### Hard limits (validator)

| Thing | Limit |
| --- | --- |
| `stars` | 1–1500 entries (also re-checked as `desiredStarCount > 1500`) |
| `players` | 2–64 entries (advanced only) |
| `carriers` | 0–500 entries |
| `naturalResources.*` | 0–2000 each |
| `infrastructure.*` | 0–200 each |
| `shipsActual` | 0–200000 |
| `credits`, `creditsSpecialists` | 0–200000 |
| `technologies.*` | 0–200 each |
| carrier `ships` | integer, **1**–20000 (0 is rejected) |
| carrier `progress` | 0–1 |
| star `name` | **3**–30 chars |
| player `alias`, carrier/team `name` | 1–30 chars |

Every star field is **required and non-defaulting** except `shipsActual`, `isKingOfTheHillStar`, and `name`:
`id`, `location{x,y}`, `playerId` (nullable), `naturalResources{economy,industry,science}`, `specialistId`
(nullable), `specialistExpireTick` (nullable), `homeStar`, `warpGate`, `isNebula`, `isAsteroidField`,
`isBinaryStar`, `isBlackHole`, `isPulsar`, `wormHoleToStarId` (nullable), `infrastructure{...}`. All IDs are
**strings**, minimum length 1.

Unknown keys are harmless: the `object()` validator copies only keys it knows about, so the extra `ships`,
`terraformedResources`, and player `colour`/`shape` this toolkit emits are silently dropped.

### Semantic rules (`validateAndCompleteCustomGalaxy`)

Always enforced: unique star IDs; no star wormholes to itself and `wormHoleToStarId` must exist (note Solaris
does **not** require reciprocal pairs, unlike the editor, which forces them — `model.link_wormhole` sets both
ends so a map stays openable there); `specialistId` must be a real specialist flagged `active.custom`;
**home stars must have a `playerId`**; **unowned stars must have 0 ships**; **dead stars** (natural resources
summing to 0) must have 0 infrastructure, no specialist, and no warp gate.

Advanced additionally enforces: unique player IDs; every `homeStarId` exists; no two players share a capital;
every star `playerId` exists; a capital's `playerId` must match the player that claims it; a star named as some
player's `homeStarId` must have `homeStar: true`. With no `carriers` array, each player must have exactly one
home star and every owned star's player must have a home star.

Carriers: `playerId` and `orbiting` must exist; an in-flight carrier (`orbiting: null`) needs ≥1 waypoint, a
`progress` value, and `delayTicks: 0` on its first waypoint; consecutive waypoints must chain
(`waypoints[i-1].destination === waypoints[i].source`). **In non-tutorial games Solaris then truncates
waypoints to the first one for in-flight carriers and to zero for orbiting ones, and forces
`waypointsLooped: false`** — so elaborate pre-set routes are wasted effort for a normal match.

### Settings Solaris overrides from the map

`playerLimit` = count of `homeStar: true` stars. `starsPerPlayer` = `starCount / playerLimit`.
`splitResources` is auto-enabled if any star has unequal economy/industry/science. All random terrain settings
(`randomWarpGates`, `randomWormHoles`, `randomNebulas`, `randomAsteroidFields`, `randomBinaryStars`,
`randomBlackHoles`, `randomPulsars`) are forced to 0. In advanced team games, `teamsCount` = `teams.length` and
`maxAlliances` = `players.length - 1`. `validate.describe_derived_settings()` prints these for a given map.

### Scale and ranges

`LIGHT_YEAR = 50` world units is what every range keys off. Hyperspace and scanning are **not** the same
formula: a carrier at hyperspace *h* jumps `(h + 1.5) × 50`, a star at scanning *s* sees `(s + 1) × 50`. A
traversed wormhole always costs exactly one tick. A black hole is worth +3 scanning, and a dead star scans
nothing at all. All of this lives in `solarismap/rules.py`, and `python -m solarismap rules --json` dumps it.
